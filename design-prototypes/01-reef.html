Durability

It forgets nothing.

A machine that sleeps is only useful if it wakes up remembering. Krill ships your SQLite write-ahead log from outside the VM — the guest is never trusted with its own durability.

Point-in-time branching is in private beta. Ask for access →
Object-storage backedEvery acknowledged write lands in the record before the reply leaves the box. The host is a cache, not the truth.
Roll back to any secondkrill restore notes --at "14:02:11" forks a new branch of the database and leaves the original untouched.
No SDK, no object-store gymnasticsYour app opens /data/app.db with the stock SQLite driver. That's the whole integration.
The fencing protocol

We proved it before
we built it.

Pausing a machine mid-request is the normal case here, not an outage. So the correctness argument can't be "we tested it." Krill's single-writer protocol is specified in TLA+ and model-checked on every commit — including three deliberately broken configurations that must keep failing.

E3The gateway refuses any reply stamped with a stale epoch.
E5A snapshot can't register itself if a newer generation already exists.
E6Restore replays the log forward before the guest is allowed to run.

TLC found the "slow waker" failure after a human review had signed off on the same design. The model won. We kept the model.

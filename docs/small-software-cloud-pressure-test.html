Part I

The fencing protocol

Context: one Firecracker microVM per app, one SQLite file per app, scale-to-zero via memory snapshots, WAL shipped to object storage. The correctness problem is single-writer enforcement when the writer can be paused for a month and resumed believing no time has passed.

1.1 Components and the trust boundary

Five parties touch an app's write path: the guest VM (agent-written code plus SQLite — untrusted), the host agent (one per machine; owns VM lifecycle, trusted), the cell control plane (lease table in a linearizable store), the storage gateway (the WAL sink, replicated per cell), and the edge router (routes requests to the current holder).

Load-bearing decision № 1

WAL shipping runs in the host agent, not the guest. The guest writes SQLite to a local block device served by the host; the host agent tails the WAL from outside the VM, stamps each segment with the epoch it holds, and ships it. A Litestream-style shipper inside the guest would put epoch stamping in untrusted hands — the guest is agent-generated code, and fencing that depends on guest cooperation is not fencing. Guest cooperation may be a performance optimization; it is never a safety mechanism.

1.2 The durability contract

  1. D1A write is acknowledged to the app only when its WAL frames are acked by the storage gateway under the current epoch. Group commit, synchronous in-region — this costs 1–5 ms of write latency, and Pressure Test 1 shows why it is not optional.
  2. D2Local NVMe inside or under the VM is a cache. It never counts toward durability.
  3. D3Gateway → object storage replication is asynchronous. Region loss costs seconds of writes (documented RPO); host loss costs zero.
  4. D4Point-in-time restore never rewrites history. "Roll the database back to 3 pm" creates a new lineage that references the old stream as a prefix — a branch, in git terms (see PT-8).

1.3 Epoch rules

The epoch is the fencing token. Six rules define it completely:

  1. E1Epoch e is a 64-bit value: cell_generation ‖ counter, compared as one integer. It is incremented by a compare-and-swap in the cell's linearizable store on every lease acquisition. The cell-generation prefix means a cell-ownership transfer fences every app in the cell at once — this closes the directory-layer split-brain (PT-4's ugly cousin).
  2. E2Every externally visible effect carries its epoch: WAL segments, snapshot manifests, router advertisements, cron-run ledger entries. No effect is unstamped.
  3. E3The gateway accepts a WAL append iff segment.epoch == stream.current, or segment.epoch > stream.current after first writing a SEAL record that terminates the old epoch's suffix. Anything lower is rejected, and rejection is a signal to the pushing host agent to kill its instance.
  4. E4The stream manifest lives in object storage, and every mutation is a conditional PUT (compare-and-swap on manifest generation). The object store — not the gateway — is the arbiter of record. Gateways are caches of it.
  5. E5Snapshot manifests carry (epoch, LSN, checkpoint_id), and registration is itself fenced: the control plane rejects a manifest whose epoch is below current. Unregistered snapshots are garbage. This rule is the non-obvious one — see PT-2.
  6. E6A resuming instance must, in order: acquire a fresh lease (new epoch e′) → replay the WAL delta from its snapshot's LSN to the stream head into its SQLite file → open the gate. No guest instruction with a network or disk effect executes before e′ is held. The host agent enforces the ordering; the guest is never asked.

The one-line theory of the design

Leases route traffic; epochs protect data. The lease is an optimization that makes the common case fast and keeps two instances from running concurrently most of the time. It is allowed to be wrong — during partitions, pauses, and clock trouble it will be wrong. The epoch checks at the gateway, the manifest store, and the control plane are the correctness mechanism, and they are never skipped, cached past a write, or delegated to the guest.

1.5 Invariants — and how I'd actually test them

  1. I1Single writer. For any app, WAL segments accepted under epoch e are never interleaved with segments from e′ < e after the seal of e′.
  2. I2No lost ack. Every client-acknowledged write is in the sealed prefix visible to the next epoch's replay.
  3. I3Snapshot lineage. Every registered snapshot's (epoch, LSN) lies on the accepted WAL history — no snapshot ever forks it.
  4. I4Monotonic wake. A resumed instance produces no externally visible effect under its pre-pause epoch.

This state space is small — one app, two or three host agents, a gateway, a manifest store — and the TLA+ spec now exists (FencingProtocol.tla). TLC checks I1–I4 across 26,618 reachable states and passes; re-run with each fence disabled in turn, it reproduces PT-1 and the stale-restore bug as counterexample traces — and produced one scenario the hand-written pressure tests below had missed entirely (PT-9, the slow waker). The next layers of assurance: a deterministic simulation harness (FoundationDB style) running the real code with fault injection at every await point, where the injector's pause primitive is first-class — because on this platform, pause is not a fault, it's the product — and Jepsen-style partition tests on a real cluster last, mostly confirming what the simulator already found.

Part II

Nine ways to kill it — the pressure test

Each scenario: what happens, what a naive design does, what this protocol does, and what risk honestly remains. Severity is the blast radius of getting it wrong: ▲critical = silent data corruption or loss, ◆serious = recoverable damage or lineage confusion, ●watch = bounded, documented weirdness. Scenarios one through eight were written by hand; the ninth was produced by the model checker after the fact — which is its own finding about hand-written pressure tests.

PT-1

The partition zombie

◆Serious
SetupHost H1 runs app instance A at epoch 5. H1 partitions from the control plane and gateway. The lease TTL expires; the router flips; instance B wakes on H2 at epoch 6, seals the stream, replays, serves.
Naive failureH1 heals. A, believing it holds the lease, pushes its buffered WAL. An unfenced sink appends it — interleaving epoch-5 writes into an epoch-6 stream. Corruption nobody notices for weeks.
Protocol's answerGateway rejects the push (E3: 5 < 6, stream sealed). Rejection instructs H1's host agent to kill A and discard local state. Crucially, under D1 A could not have acked any write after the partition began — the gateway was unreachable — so no acknowledged write is lost. Async shipping would break exactly this promise, which is why sync-in-region is the default.
Residual riskA served stale reads during the partition window — bounded by the TTL. See PT-6.
PT-2

Zombie snapshot resurrection

▲Critical
SetupA is mid-snapshot on an overloaded host — slow NVMe, the pause is taking 40 seconds — when its lease expires. B takes over at epoch 6 and writes 150 new WAL entries. A's snapshot then finishes, with DB state at epoch 5, LSN 100.
Naive failureThe snapshot gets registered — it has the newest wall-clock timestamp, so the next wake restores it. Users see the database jump backward in time; new writes fork the lineage from LSN 100. This is the nastiest scenario in the design because every individual step looks locally reasonable.
Protocol's answerTwo independent fences. First, registration is a fenced CAS (E5): epoch 5 < current 6 → rejected, snapshot garbage-collected. Second, even a stale manifest that somehow lingered is harmless, because restore (E6) always replays the WAL delta from the snapshot's LSN to head — which requires the snapshot's SQLite to sit at an exact checkpoint boundary. That is why SEALING checkpoints before snapshotting memory, not after.
Residual riskNone to data content. But the claim that a stale manifest is otherwise harmless was too strong: PT-9 — found later by the model checker — shows the manifest's lineage metadata has its own failure mode, and E5 is the only fence that catches it.

PT-2 resolved: the snapshot that finished last loses to the epoch that was granted last. Wall-clock recency is never trusted anywhere in the protocol.

PT-3

Paused clocks — the platform's defining hazard

▲Critical
SetupThe classic distributed-systems bug: a lease holder checks "valid until T," then stalls (GC, kernel hiccup), then acts after expiry. On a normal platform that's a rare race. Here, arbitrary pause is the normal operating mode — a VM can freeze mid-request and resume three weeks later with a valid-lease belief intact in its memory image.
Naive failureAny design where the lease timer lives inside the VM — or where resume trusts in-memory state at all — ships corrupted writes on literally every long suspend. This isn't a tail risk; it's the common case.
Protocol's answerLeases are held by the host agent on behalf of the instance, never inside it, and every pause/resume boundary re-runs the lease CAS before the guest executes one post-resume instruction (E6). And because host agents can stall too, the lease is never the last line: every effect is individually fenced downstream (E2–E5). The lease can be wrong; the epoch check cannot be skipped.
Residual riskNone if E6 ordering is enforced in the hypervisor control path. This invariant (I4) is the one to model-check hardest and the reason the TLA+ spec must include pause as a first-class action.
PT-4

Storage gateway split brain

◆Serious
SetupThe gateway is replicated per cell. Two replicas hold divergent views of an app's current epoch — one missed the seal.
Naive failureEach replica appends what it believes is valid; the object-storage stream interleaves two epochs. Fencing at a component that is itself unfenced is no fencing at all.
Protocol's answerGateway epoch state is cache only (E4). The authoritative act is a conditional PUT against the stream manifest in object storage — compare-and-swap on manifest generation. S3-class conditional writes make the object store the single serialization point; a confused gateway's append simply fails its precondition. Throughput is a non-issue by construction: small software is low-QPS per app, and frames group into ~1 MB or 1-second segments.
Residual riskManifest CAS adds one object-store round trip per segment (~10–20 ms, hidden behind group commit). Object-store conditional-write semantics become a hard vendor requirement.
PT-5

Dueling wakers

●Watch
SetupTwo requests hit two edge nodes simultaneously for a frozen app. Both trigger wakes; two host agents race to restore.
Protocol's answerThe cell scheduler coalesces wake requests by app id, but coalescing is best-effort — correctness comes from the lease CAS alone: exactly one contender gets epoch e+1; the loser aborts its prefetch and the router converges on the winner.
Residual riskAn occasionally wasted snapshot fetch. Accepted; optimizing it below ~1% of wakes isn't worth complexity.
PT-6

Stale reads from the routed-around zombie

●Watch
SetupFencing protects writes. A zombie holding an in-flight or long-poll connection can still answer reads with pre-failover data — someone updates the on-call roster via B while a colleague's open tab reads stale from A.
Protocol's answerTwo bounds. The router consults the lease on every new connection, so new reads never reach a zombie. Existing connections are bounded by staleness ≤ lease TTL + max clock skew (~20 s at a 15 s TTL). For a five-user tool this is honest and acceptable — document it rather than hide it. A strict mode (reads revalidate epoch at the gateway, +1 RTT each) exists for the rare app that needs linearizable reads.
Residual riskThe documented window itself. The TTL becomes a product knob: shorter TTL → smaller window, more control-plane heartbeat load, more spurious failovers.
PT-7

Cron double-fire

●Watch
SetupScheduler wakes an app for a cron job; the job runs, sends an email, and the completion ack is lost. At-least-once delivery retries; the lease prevents concurrent instances, but nothing prevents a sequential re-run.
Protocol's answerFencing cannot fix external side effects — exactly-once I/O to the outside world doesn't exist. Instead the platform provides idempotency as a primitive: a job-run ledger keyed (app, job, scheduled_time) living in the app's own WAL-backed state (so it inherits I1–I2), and platform egress APIs (email, webhooks) that accept dedupe keys.
Residual riskAgent-written code that bypasses platform egress APIs loses the guarantee. Mitigation is the egress proxy: raw outbound effects are already gated for security reasons, so the idempotent path is also the easy path.
PT-8

Time-travel restore vs. the lineage

◆Serious
SetupA user says "roll the database back to 3 pm" after their agent's migration ate a column. Naively you truncate the WAL to 3 pm and resume — but replicas of the truncated suffix exist (snapshots, caches, the gateway), and a future PT-2-style race can resurrect them into a stream that now claims those LSNs never happened.
Protocol's answerD4: restore is a branch, never a rewrite. It bumps the epoch and opens a new stream whose manifest references the old one up to the restore LSN as an immutable prefix. Old suffixes stay sealed under their epochs forever — inert, but present. Bonus: the branch model is the product's revision-history feature; undo, audit, and "what did this look like Tuesday" fall out of the correctness design for free.
Residual riskStorage growth from retained suffixes — bounded by the PITR retention window (priced into Part III at 1.4×).
PT-9

The slow waker — found by the model checker, not by this review

▲Critical
SetupA host acquires the lease at epoch e, then stalls before rehydrating — a host-agent hiccup on an overloaded machine. The TTL expires; a successor takes epoch e+1, seals, and writes. The stalled waker then finishes its rehydration — replaying the successor's writes into its own state — goes active, idles out, and registers a snapshot manifest stamped epoch e whose prefix contains epoch-e+1 data.
Naive failureThe manifest lies about lineage. The data content is coincidentally correct; the ancestry is forged. PITR branching (D4) and garbage collection both trust manifest epochs, so a forged ancestor can orphan live suffixes or attach a branch to the wrong history — silent data loss, one hop removed. And the gateway fence never fires, because the slow waker never appends a single WAL segment.
Protocol's answerE5, and only E5. The registration CAS rejects epoch e against current e+1; the instance dies. This retires the idea that fenced registration is defense-in-depth — on this path it is the sole fence. Implementations should additionally make the takeover seal a fenced gateway write, so a stale waker dies at rehydrate via E3's reject clause — belt and suspenders, but E5 is the one guaranteed to be there.
Residual riskNone with E5 enforced. Provenance: TLC produced this trace within seconds of switching registration fencing off in FencingProtocol.tla — after a human review had predicted that configuration was safe. The eight scenarios above were all written by hand and all missed it; that asymmetry is the argument for keeping the spec alive as the protocol evolves.

What the pressure test changed — seven design commitments

  1. WAL shipping moved out of the guest into the host agent. Epoch stamping can't live in untrusted, agent-generated code (§1.1).
  2. Leases route; epochs protect. The lease was demoted to an optimization — every effect is individually fenced downstream, because on this platform pause is the product, not a fault (PT-3).
  3. Snapshot registration is fenced — the non-obvious rule. Without E5, PT-2 silently forks user data, and wall-clock recency would pick the wrong snapshot every time. The model checker later hardened this from "non-obvious" to "load-bearing": on the slow-waker path (PT-9), E5 is the only fence.
  4. Sync in-region WAL shipping is the default, not a paranoid option: it is what makes PT-1 lose zero acknowledged writes. 1–5 ms of write latency buys the durability contract.
  5. SQLite checkpoints before memory snapshots, so every snapshot sits on a replayable WAL boundary (PT-2's second fence).
  6. Point-in-time restore is branching, never truncation — and doubles as the revision-history feature (PT-8).
  7. The takeover seal must be a fenced gateway write, never elided as redundant with the lease. The slow waker (PT-9) is exactly what slips through when an implementation reasons "we just acquired the lease, skip the seal round-trip."

Part III

Unit economics, with the assumptions on the table

The claim from the brainstorm was that an idle app must cost about a cent a month for the business to work. Here is the model behind that claim — cohort-based load assumptions, a live calculator, and the sensitivity analysis showing where it breaks.

3.1 The load model

Small software's traffic is human-paced and bursty. Rather than one made-up average, the model uses three cohorts. An app is "awake" from first request until a 5-minute idle timeout; session lengths below include that trailing window.

CohortShareUsage patternAwake timeDuty cycle
Hot3%Team dashboards and trackers in daily use — ~8 wake-sessions per weekday × 12 min~96 min/weekday≈ 4.8% blended
Warm22%Weekly tools, prototypes being iterated — ~1.5 sessions/day × 9 min~13 min/day≈ 0.9%
Dormant75%Finished experiments, seasonal tools — ~1 wake per two weeks, plus stray cron~8 min/fortnight≈ 0.04%

Blended: 0.03 × 4.8% + 0.22 × 0.9% + 0.75 × 0.04% ≈ 0.4% duty cycle — the model's default, and a single slider below so you can disagree with it. The peak factor captures the correlation problem: wakes cluster at 9 am Monday because small software is synchronized to human work rhythms, so peak concurrency is taken as peak-factor × mean, plus 25% headroom.

3.5 Where the model breaks

  • Duty cycle drifting up. Past ~3–5% blended duty, RAM-seconds dominate and the scale-to-zero machinery buys little; near 10% you converge with always-resident (chart 3.4). Product implication: always-hot apps must be metered or priced separately — the free tier is free because it sleeps.
  • The peak factor. At peak factor 6 the fleet is sized 7.5× above mean load. If correlated wakes push it to 12–15 (every standup dashboard, 9:00:00 sharp), the compute line roughly doubles. Jittered cron, wake-rate admission control, and calendar-aware pre-warming aren't nice-to-haves; they are margin.
  • Snapshot bloat. Agents produce 1.5 GB node_modules without blinking. At face value that quadruples storage — the biggest line-item risk in the model. Content-addressed, chunk-deduplicated snapshots (most apps share base-image pages) are load-bearing and must be built early, not retrofitted. The 220 MB default assumes roughly 4× dedupe.
  • Abuse eats the margin. The CPU assumptions hold only if cryptominers are evicted fast. Free arbitrary-code hosting attracts them on day one; detection and caps are part of COGS, not an afterthought.
  • What the comparison is fair to. The always-resident baseline is the naive per-app reservation that incumbent-cloud pricing passes on to you. A tuned Kubernetes fleet with aggressive overcommit narrows the gap — but it cannot delete the idle-RAM floor, and it reintroduces exactly the operational complexity this cloud exists to delete.

3.6 Bottom line

At the defaults — a million apps, 0.4% duty — the whole platform runs on about two dozen hosts for roughly $20k/month: two cents per app, a third of a cent for an idle one, about 17× cheaper than the naive architecture, and infrastructure COGS under 2% of even conservatively modeled revenue. The margin structure of a SaaS company with the workload of a hosting company — but only if the fencing protocol in Parts I–II holds, because the same snapshot machinery that creates the margin is what creates the zombies.

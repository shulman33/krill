The Sleeping Cloud — Architecture

Six views of the system, one idea per view. Colors mean the same thing in every diagram; the dark pills mark exactly where an epoch check is enforced — rule numbers refer to the protocol document.

D1

The system at a glance

Two kinds of client — a teammate using an app, and the coding agent that deploys it — meet the platform at the edge. Everything stateful lives inside cells: self-contained groups of 50–200 hosts with their own control plane, so a bad day stays inside one cell. The global layer is deliberately thin, and object storage — not any server — is the arbiter of record.

  • The global layer holds no app data. It maps app → cell and users → orgs. If it degrades, running apps keep serving; only new lookups slow down.
  • Cells are the blast radius. Each has its own lease table and gateway. A control-plane bug takes down wakes in one cell, not the platform.
  • The gateway is a cache of the truth, not the truth. Every manifest mutation is a conditional write to object storage (rule E4) — which is why gateway split-brain is survivable (pressure test PT-4).
D2

Life of a request — waking a frozen app

The defining flow of the platform. A request arrives for an app that doesn't exist in RAM anywhere. The router parks the request, orchestrates a wake, and replays it — the user experiences one slow request, never an error. The time ruler shows where the 300 ms budget (gate G1) actually goes: nearly all of it is the snapshot restore.

  • Steps 4 and 5 overlap. The snapshot prefetch can begin optimistically before the lease CAS lands — but no externally visible effect happens until the new epoch is held (rule E6).
  • The lease CAS is the only global coordination point, one conditional write in the cell's store. Everything else on the critical path is host-local I/O.
  • Warm apps skip almost all of this: if the app is already resident, the router forwards directly and the whole left half of the ruler collapses to ~2 ms.
D3

Inside one host — the trust boundary

One bare-metal machine runs one trusted host agent and many Firecracker microVMs full of code nobody reviewed — agents wrote it. The dashed line is the design's most important commitment: everything that matters for correctness (leases, epoch stamps, WAL shipping) happens on the host-agent side. The guest is never asked to cooperate with its own containment.

  • The guest sees an ordinary Linux disk. Its SQLite writes land on a virtio block device served by the host, and the host agent tails the WAL from outside the VM — that's how epoch stamping (rule E2) stays in trusted hands.
  • The guest has no network path to the gateway or control plane. Its egress goes through a policied proxy; its durability goes through the host agent. A prompt-injected app can misbehave, but it cannot forge an epoch.
  • Density comes from the frozen majority: the ghost box is the point — hundreds of thousands of apps are resident on this host as NVMe snapshots costing zero RAM.
D4

The write path — every effect fenced

Follow one INSERT from untrusted code to durable, fenced storage. The two dark pills are where a stale writer dies: the gateway refuses WAL segments from a superseded epoch (E3), and the object-store manifest only mutates via compare-and-swap (E4). The ack flows back only after the gateway accepts — that ordering is the durability contract D1, and it's why a partition zombie can never lose an acknowledged write.

  • Group commit hides the sync cost: WAL frames batch into ~1 MB or 1-second segments, so the +1–5 ms in-region round trip is paid per batch, not per statement.
  • A rejected segment is a death sentence, by design. The gateway's refusal tells the host agent its instance is a zombie; it kills the VM and discards local state (pressure test PT-1).
  • Cross-region replication is async — region loss costs seconds of writes (documented RPO, contract D3); any single host or gateway loss costs zero.
D5

Snapshot heat tiers — where apps live and what they cost

The economics of the whole company in one picture. An app moves right as it cools — each demotion is a policy decision made by the platform — and moves left instantly on demand. At any moment ~95% of all apps sit in the rightmost tier costing about a third of a cent a month, which is what makes “as free as a Google Doc” a real price.

  • Demotion is policy, promotion is demand. The platform chooses when to snapshot and evict (idle timers, LRU, calendar-aware prediction); users choose when to wake, and the router absorbs the latency by holding the request.
  • Every tier transition is fenced: snapshotting registers a manifest (E5 — checked), waking acquires a fresh epoch (E6 — enforced). The tier diagram and the state machine in the protocol doc are the same object at two zoom levels.
  • Snapshot bytes are content-addressed and deduplicated across apps sharing base images — the ~4× dedupe assumption is what the Phase-4 benchmark exists to verify.
D6

Sharing & identity — auth is the platform's job, never the app's

Why sharing agent-built software can be as safe as sharing a document: the app contains zero authentication code. TLS terminates at the edge proxy, which authenticates the person, checks the app's ACL, and forwards the request with a signed identity assertion scoped to that one app. The app reads a header it can cryptographically trust — and credentials never reach untrusted code.

  • Three permission planes, deliberately separate: who can use the app, who can edit it (which increasingly means “point their agent at it”), and who can read its data — the plane people forget until an app's SQLite holds other people's submissions.
  • ✕ There is no direct network path from user to app. Every request crosses the proxy, so revoking a share takes effect on the next request — no app redeploy, no key rotation.
  • The assertion is scoped to one app. A malicious or prompt-injected app can see who's using it; it cannot replay that identity against any other app or service.

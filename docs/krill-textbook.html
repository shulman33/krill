The Sleeping Cloud

Four short chapters on how to run a million tiny apps that are asleep almost all the time — and wake in the time it takes to blink. Each chapter teaches the general idea first, then shows the real implementation in this repository.

Everything measured in this book was measured on real hardware (GCP nested virtualization, 2026-07-23). Identifiers like E1–E6 and PT-9 are the project's actual cross-reference system — the same labels appear in the TLA+ spec, the design docs, and the code.

Prologue

A cloud for small software

Every cloud you have used was designed around one assumption: that software is awake. Krill is an experiment in deleting that assumption.

AI assistants now write little applications constantly — a vacation-day tracker, a rota generator, a five-person expense splitter. Call this small software: apps with a handful of users, touched a few minutes a day. The economics of normal clouds are absurd for them. A container that idles 99.6% of the time still pays rent 100% of the time, and "sharing the app with a colleague" still means accounts, logins, and deployment ceremony.

Krill's bet is that a small app should behave like a document: cheap to keep, one click to share, instantly there when opened. The mechanism behind the bet:

Scale to zero. When an app is idle, it does not run slowly or run small — it stops existing as a process. Its entire machine state (memory, devices, registers) is written to disk as a snapshot. A visitor's HTTP request brings it back. If the resurrection is fast enough, the visitor never knows the app was gone.

At the project's modeled scale — one million apps at a 0.4% duty cycle — the fleet costs about $20k/month, a third of a cent per idle app: roughly 17× cheaper than keeping the same apps resident. The entire system exists to make that number real without breaking two promises: never lose an acknowledged write, and never let two copies of an app both think they're real. Chapter 3 is about how hard those promises are.

The cast of characters

Five actors appear in every chapter. The colors are a fixed language used across all of this project's diagrams — learn them once and every later figure reads faster.

One design stance shapes everything: the guest is untrusted. The app's code was written by an AI on a user's behalf; it may be buggy, hostile, or both. So the guest is never asked to help with correctness — it isn't trusted to stamp its own writes, keep time, or report its own health. Every safety mechanism in this book lives on the host side of the wall.

The milestones map cleanly onto the chapters: M1 makes one host sleep and wake apps, M2 gets apps onto the host in one call, M3 makes their data survive anything, and M4 puts identity at the front door. Each milestone shipped against pre-registered acceptance gates — pass/fail criteria frozen before the code was written, then run on real hardware. You'll meet them at the end of each chapter.

Milestone M1 · the host agent

Machines that sleep

What you'll learn
  • Why untrusted code gets a whole (micro) virtual machine, not a container
  • How snapshot/restore turns "boot the server" into "resume the server" — and what that costs in milliseconds
  • How a request to a sleeping app is held, not refused: the wake-on-request pattern
The concept

1.1 A machine small enough to keep in a file

A virtual machine is a lie told by hardware: the CPU (via KVM on Linux) lets a host run a guest operating system that believes it owns a computer. The guest has its own kernel, so even a malicious program inside it must break through two walls — its kernel, then the hypervisor — to touch the host. That isolation is why VMs, not containers, are the right home for code written by someone else's AI: containers share the host's kernel, and a shared kernel is a shared attack surface.

Historically VMs were heavyweight — minutes to boot, gigabytes of overhead — because they emulated a full PC: BIOS, PCI bus, VGA card, floppy controller. A microVM deletes the nostalgia. Firecracker (the VMM built for AWS Lambda) emulates almost nothing: a virtio disk, a virtio network device, a serial console, and that's about it. A guest kernel boots in ~150 ms, and each VM costs megabytes, not gigabytes. You control it over a local API socket: create machine → attach kernel and disk → attach network → start.

microVM. A virtual machine with a minimal device model, designed to be created and destroyed like a process while retaining hardware-level isolation. Krill runs every app in one.
The concept

1.2 Snapshot/restore: sleep instead of shutdown

Booting even a fast VM means running a kernel's init, starting a runtime, importing libraries. But there is a second path. Pause the VM, write its guest memory and device state to two files, and kill the process. Later, map those files back into a fresh VMM and resume: every process inside continues from the exact instruction it was on, TCP listeners still listening, caches still warm. The guest does not know time passed. This is snapshot/restore, and it converts "start the app" (hundreds of ms to seconds, running your code) into "restore the machine" (a memory-mapping problem with a fixed cost).

The benchmark that green-lit this whole architecture measured the gap on real hardware: booting the guest cold took 1,649 ms; resuming it from a snapshot took 114 ms (p50) — a 14.5× win, with each sleeping app costing ~69 MB of disk after deduplication. Cheap enough, fast enough: commit.

The concept

1.3 Wake-on-request: hold the door

Who wakes a sleeping app? The elegant answer: its own traffic. A reverse proxy sits in front of every app. When a request arrives for a frozen app, the proxy does not return an error — it holds the request, asks the host agent to restore the snapshot, waits for the guest to answer, then forwards the held request as if nothing happened. To the visitor, a sleeping app is indistinguishable from a running one, except the first click costs an extra fraction of a second.

Two disciplines make this honest. First, single-flight: if fifty requests arrive for the same frozen app, exactly one wake happens; the other forty-nine wait on it. Second, measure on the host: a guest's clock jumps forward across resume (it slept; its clock didn't), so any latency measured inside the guest is fiction. Every number in this book was taken on the host side.

In Krill

1.4 krilld: one daemon, five jobs

krilld is a single Go daemon composed of packages that map one-to-one onto the concepts above: internal/firecracker drives the VMM's API socket (the exact call sequence was ported from the benchmark's shell scripts, then pinned by tests); internal/registry is a SQLite catalog of every app — its rootfs, snapshot paths, state, and network identity; internal/network gives each app a tap device and its own /30 subnet; internal/rootfs manages a golden disk image per app plus a fresh copy-on-write clone per resume; and internal/lifecycle owns the state machine that ties them together.

In Krill

1.5 The anatomy of a wake, in milliseconds

M1's headline gate (A1) demanded: curl a frozen app, get a 200, warm-wake p99 ≤ 300 ms over 100 wakes. It passed at 298 ms — and the instrumented breakdown is more interesting than the pass:

Field notes · learned on hardware, kept forever

The ARP race. A restored guest's ARP cache is a photograph of the network at snapshot time. Give a tap device a random MAC on resume and the guest will confidently send packets to a MAC that no longer exists — for 30 seconds, the app is deaf. The fix is deterministic: each app's tap MAC is derived from its identity, so the photograph stays true. Corollary: the host pins neighbor entries, because the host-side ARP path races the resume in the other direction.

Never resume memory against a mutated disk. A memory snapshot embeds the guest kernel's beliefs about its filesystem (page cache, inode state). Resuming it over a disk that changed is silent corruption. Every resume therefore gets a fresh copy-on-write clone of the golden rootfs — and snapshots never cross a Firecracker version, kernel, or CPU-type boundary.

The balloon tradeoff, measured. Inflating a memory balloon before snapshotting shrinks the file by ~32 MB/app but costs ~6 s of freeze time, with zero effect on wake latency. Default: on. Flag: --snapshot-balloon=false.

Check yourself
Why microVMs instead of containers, when containers are lighter?

The tenant code is agent-written and untrusted. Containers share the host kernel, so one kernel bug is a full-host compromise. A microVM interposes a second kernel and a minimal hypervisor between tenant and host, while Firecracker keeps the per-VM cost close enough to a container's for the economics to survive.

Fifty requests hit the same frozen app at once. How many snapshot restores happen, and what do the other requests do?

One. Wakes are single-flight: the first request triggers the restore, the rest park on the same in-flight wake and are all replayed to the guest when it answers.

Why is a latency number measured inside the guest worthless?

The guest's clock jumps across resume — it was frozen while the world moved on. Only host-side clocks observe the wake continuously, which is why every gate measures from the host (and why Chapter 3's protocol will refuse to trust guest-side timers for leases, too).

Milestone M2 · the deploy path

From folder to URL

What you'll learn
  • Why a container image isn't a bootable machine, and what it takes to make one
  • What "deploy in one call" really requires: verification and legible failure, not just upload
  • How the platform meets its real customer — an AI coding agent — through MCP
The concept

2.1 An image is not a machine

Chapter 1's VMs need two artifacts to boot: a kernel and a root filesystem — a block device holding the app's files. The world's lingua franca for describing an app's files is the Dockerfile, so Krill accepts one. But docker build produces a container image: a stack of filesystem layers meant to run under a host's existing kernel, with no init system, often no network tooling, sometimes not even a shell. A VM, by contrast, boots into the void — PID 1 is whatever you say it is, and nobody has configured the network card.

So a deploy pipeline for microVMs has one essential job: flatten a container image into a bootable disk, and supply the missing first breath — the init program that mounts the basics, brings up networking, and hands control to the app's own command.

The concept

2.2 A deploy is a claim, so verify it

"Deploy in one call" is easy to fake: accept the upload, return a URL, hope. The honest version treats the URL as a claim — "this app now serves traffic" — and refuses to return it unverified. And because the deployer here is usually an AI agent iterating in a loop, failure must be as legible as success: a broken app should return its own stack trace in the deploy response, not a generic 500 to be excavated from remote logs. Fast, truthful feedback is the entire developer experience when the developer is a machine.

In Krill

2.3 The pipeline: tar in, golden disk out

Deploying is one HTTP call: POST /v1/apps/{name}/deploy with a tar.gz of the app directory. Server-side, internal/builder runs the flattening:

In Krill

2.4 The network contract, or: the kernel does the plumbing

Each app owns a /30 subnet (172.16.N.0/30, allocated by the registry as the smallest free slot) which determines its tap device, both IPs, and both deterministic MACs — the network identity survives redeploys. The find of the milestone: the Firecracker CI kernel is built with CONFIG_IP_PNP, so krilld appends ip=<guest>::<gw>:<mask>::eth0:off to the boot arguments and the kernel itself configures eth0 before userspace starts. Images need no iproute2, no ifconfig, nothing — genuinely arbitrary Dockerfiles deploy unmodified. (The generated init still brings up the interface when tools exist, as a fallback.)

In Krill

2.5 Two front doors: a CLI for humans, MCP for agents

Both clients are thin wrappers over the same loopback admin API. krill deploy ./dir gives humans the one-liner (plus apps, status, logs, wake, freeze, delete). The TypeScript MCP server (mcp/) exposes deploy, logs, apps, and delete_app as tools — so a coding agent's "deploy this" becomes one tools/call that returns a URL, closing the loop the platform was designed for: an AI writes an app, an AI deploys it, a human just gets a link. Gate B4 proved that path end to end.

Field notes

Contracts change; gates record which era they tested. In M2, redeploy deliberately reset app data — the disk is rebuilt from a new golden image, and durable data wasn't built yet. Gate B2 asserted that reset. M3 then added the separate /data disk, and the contract flipped: redeploys now preserve data, and B2's assertion is a historical record, not a current promise.

Small tools bite too: Go's flag package stops parsing at the first positional argument, so krill deploy ./dir --json silently ignored --json and cost the first gate run. The CLI now parses flags in any position.

The next trust boundary is the build itself. Notice what this chapter quietly did: it runs docker build on the host, against an uploaded context — attacker-supplied instructions executing during the build, outside any microVM. That's acceptable while the only deployer is the platform's owner, and the recorded plan (ROADMAP decision #8) closes it before anyone untrusted can deploy: rootless BuildKit, kaniko, or the self-respecting option — running builds inside a throwaway Krill microVM.

Check yourself
Why does docker build output need an injected init script before a microVM can use it?

A container image expects a host kernel with namespaces already set up around it. A VM boots bare: something must be PID 1, mount /proc//sys//dev, get the network up, and exec the app's command. krill-init.sh is that something, generated per app from the image's own metadata.

What makes it safe to deploy an image that contains no networking tools at all?

The guest kernel has CONFIG_IP_PNP, and krilld passes the app's addresses via the ip= boot argument — the kernel configures eth0 itself, before any userspace runs. The image contributes nothing to networking.

Why is returning the app's traceback in the deploy response worth gate status (B3)?

Because the deployer is usually an agent in a fix-and-retry loop. A structured traceback in the response is the difference between one-shot self-correction and a blind guessing game against a generic error page.

Milestone M3 · the data plane

The data plane

What you'll learn
  • The two classic distributed-systems demons — lost writes and split brain — and why a sleeping cloud summons both on purpose
  • Fencing: how monotonically increasing epochs, checked at the storage layer, make a stale writer harmless
  • How a formal spec (TLA+) caught a bug nine hand-written scenarios and a human review missed — and then became a permanent test oracle

Chapters 1 and 2 built a cloud that sleeps. This chapter makes it safe for the apps to trust it with their data — which is harder than it sounds, because a machine that can be paused at any instant and revived weeks later is a machine that breaks most textbook assumptions on purpose.

The concept

3.1 What "saved" means: the durability contract

Every storage system owes its users one crisp definition: at what moment is a write safe? The honest answer can't be "when the app's local disk has it" — hosts die, and in Krill an app's local disk is rebuilt routinely. So the contract, stated up front as four rules:

RuleThe promise
D1A write is acknowledged only after its WAL frames are accepted by the storage gateway under the current epoch. Durability before ack, always — costs a few ms of write latency.
D2Local NVMe is a cache. It never counts toward durability, no matter how fast it fsyncs.
D3Gateway → object storage replication is async: losing a host costs zero writes; losing a region costs a documented few seconds.
D4Point-in-time restore never rewrites history. "Roll back to 3 pm" creates a branch — a new lineage referencing the old one as an immutable prefix.
Write-ahead log (WAL). Instead of editing the database file in place, SQLite first appends each transaction's changed pages to a log file. The log is the recent history of the database — which makes it the perfect unit to ship somewhere safer. Krill's whole data plane is, at heart, a machine for moving one SQLite WAL into object storage correctly.
The concept

3.2 The second writer: split brain

Here is the founding nightmare of distributed systems. Host 1 runs your app. The network between Host 1 and the world hiccups. The platform, unable to reach Host 1, reasonably concludes it's dead and starts the app on Host 2. But Host 1 isn't dead — it's partitioned, still running, still buffering writes. When the network heals, two hosts both believe they own the same database. This is split brain, and the project's pressure-test catalog opens with it as PT-1, "the partition zombie."

Note what fencing does not do: it doesn't prevent the zombie from existing, running, or trying. It makes the zombie's writes unable to land. Prevention is impossible in an asynchronous network; harmlessness is achievable.

The concept

3.3 Why leases lie on this platform

The standard tool for "who currently owns X" is a lease: a lock with an expiry time, renewed by heartbeat. Leases are fine — until you ask who checks the clock. A lease holder that stalls (GC pause, scheduler hiccup) can wake up past its expiry and act on a belief that has quietly become false. In most systems that's a rare misfortune. In Krill it is the normal operating mode: freezing a VM mid-request and resuming it weeks later is the product. An in-guest lease timer would be wrong after every single nap. This is PT-3, "paused clocks" — the platform's defining hazard, and the reason Chapter 1's rule ("never trust guest time") returns here as a correctness principle.

The design stance: leases route, epochs protect. Krill still uses leases — held by the host agent, never the guest — but only as an optimization that decides who probably should run. The lease is allowed to be wrong. Correctness comes from every externally visible effect being individually checked downstream, against a fencing token.
The concept

3.4 Epochs: a number that only goes up

A fencing token (Krill calls it an epoch) is a counter incremented every time ownership of an app changes hands. Every wake mints a fresh, strictly larger epoch. Every effect the instance produces — every WAL segment, every snapshot manifest — is stamped with the epoch it was produced under. Now any downstream system can settle "is this writer current?" with an integer comparison, no clocks involved. A stalled, partitioned, or long-frozen writer carries a small number into a world that has moved on to a bigger one, and every door closes politely in its face.

Two refinements make the idea industrial-strength. First, the epoch is a composite — cell_generation ‖ counter, compared as one 64-bit integer — so if the control plane itself is ever rebuilt, bumping the generation instantly out-ranks every number minted before the loss. Second, the arbiter must be the storage, not a server in front of it. Gateway processes can split-brain too (PT-4). So the authoritative record — the stream manifest — lives in object storage, and every mutation is a conditional PUT: "write this only if the manifest's generation is still G." Two racing writers both try; the object store, which is linearizable, lets exactly one win; the loser re-reads and re-decides. The gateway is merely a cache of what the object store has agreed to.

In Krill

In Krill

3.6 Shipping the WAL from outside the VM

Recall the stance: the guest is untrusted, so the guest cannot ship its own writes (a hostile app could stamp any epoch it likes — that isn't fencing, it's asking nicely). Instead the host reads the guest's database from outside. Since M3, every app gets a second virtio disk mounted at /data, holding its SQLite file. The host can read that disk image directly — which sounds simple and hides two lovely problems.

First, parsing: the host reads raw SQLite WAL bytes with its own parser (internal/sqlitewal), trusting nothing. The WAL format helps — every frame is covered by a cumulative checksum chain, so a torn or in-progress write self-invalidates, and the parser replays only up to the last complete commit boundary. Second, freshness: after a guest fsync, the newest ext4 metadata (a file's size, even its directory entry) may exist only in the filesystem's jbd2 journal, not yet in the main structures. So the host's read-only ext4 reader (internal/ext4) replays the journal — the same recovery a kernel performs mounting a crashed disk — before trusting any metadata. Get this wrong and you'd ship stale data while believing yourself current.

Field notes

WAL resets are normal, not exceptional. SQLite periodically checkpoints and restarts its WAL (by default after ~1000 pages) — under a tailing shipper, the log it's reading vanishes and restarts. The shipper detects it (the WAL's salt values change) and answers with a rebase segment: a full database image at one LSN. Durability is never at risk; point-in-time granularity just coarsens across the jump.

The durability boundary is the guest's fsync. An app running synchronous=NORMAL has commits SQLite itself would lose on power cut — the tailer can't see them either, and sync-ack can't hold for what's invisible. Apps wanting the full D1 guarantee run synchronous=FULL.

In Krill

3.7 Waking without lying, and time travel without rewriting

The dangerous moment is the wake. PrepareWake runs the E6 sequence before one guest instruction executes: mint a fresh epoch (E1), write a fenced takeover seal into the manifest (a real CAS write — so a stale waker dies right here, before it can serve a byte), then compare the local /data disk against the durable history and rebuild it from the object store if it has diverged. Restore-from-nothing is the same path: latest checkpoint at-or-below the target, plus WAL-delta replay to the head. Gate C1 made this concrete: SIGKILL the app, delete every app-local file, and all 200 acknowledged rows come back byte-identical from the object store alone.

Point-in-time restore honors D4: history is never truncated (a deleted suffix could always be resurrected by some replica that still has it — PT-8). Instead, krill restore --at-time creates a branch: a new stream whose manifest references the parent stream as an immutable prefix up to the restore point. The parent, including the "bad" suffix you rolled back past, remains intact and recoverable — rollback and revision history become the same feature.

The concept

3.8 Proving it: the model checker as a colleague

How do you trust a protocol like this? Testing samples reality; a model checker exhausts a small universe of it. The protocol is written as a TLA+ specification (FencingProtocol.tla): state variables (the WAL, the manifest, each host's beliefs), actions (acquire a lease, write, seal, crash, lease-expires-without-telling-the-holder — the action that creates every zombie), and invariants that must hold in every reachable state. TLC, the checker, then explores all 26,618 reachable states. The four invariants are the moral core of the chapter:

InvariantWhat must always be true
I1Single writer: after an epoch is sealed, no earlier epoch's segments ever interleave into the stream.
I2No lost ack: every client-acknowledged write is in the prefix the next epoch replays.
I3Snapshot lineage: every registered snapshot lies on the accepted history — no snapshot forks it.
I4Monotonic wake: a resumed instance produces no effect under its pre-pause epoch.

Just as important is checking that the model can fail. The spec has three fence switches — gateway fencing (E3/E4), replay-on-restore (E6), registration fencing (E5) — and CI flips each one off and asserts TLC finds a counterexample. A fence that can't fail when disabled is a fence the model no longer exercises.

The PT-9 story · why this project trusts machines over prose

Before the spec existed, the design was pressure-tested by hand: eight adversarial scenarios, all resolved. A human review concluded that registration fencing (E5) was defense-in-depth — nice, but redundant. Then the fence toggles went into the spec, and within seconds of switching E5 off, TLC produced a trace no human had written:

A host acquires epoch e and stalls before rehydrating. Its lease expires; a successor takes e+1, seals, and writes. The stalled waker then finishes its replay — faithfully absorbing the successor's e+1 writes into itself — serves briefly, idles out, and registers a snapshot stamped epoch e whose contents contain epoch-e+1 data. The manifest forges its own ancestry. Nothing fails today; the poison waits inside PITR branching and garbage collection, one hop removed. And the gateway fence never fires, because the slow waker never appends anything — it only registers a snapshot. E5 is not defense-in-depth. On this path it is the only fence there is.

This became PT-9, "the slow waker," and the house rule it justifies: when prose and spec disagree, the spec wins, and the prose gets fixed — never the reverse without a TLC run proving it.

M3's last move closes the loop between model and reality: a deterministic simulation harness (internal/dataplane/sim) executes the spec's actions, at the spec's atomicity, against the real gateway, manifest, and object-store code — asserting every invariant after every step, over thousands of seeded random schedules. And crucially, it inherits the negative discipline: flip any of the same three fence switches off and the harness must reproduce the TLC counterexample against real code. Gate C4: 10,000 positive seeds clean; PT-1 reproduced at seed 0, the E6 stale-restore bug at seed 0, and PT-9's forged lineage at seed 1428.

Check yourself
Why can't the guest stamp its own writes with an epoch?

The guest is untrusted, agent-written code. A stamp applied by the thing being fenced is a promise, not a fence — a buggy or hostile guest could stamp anything. So the host tails the guest's WAL from outside the VM and applies the stamp itself; the guest doesn't even know epochs exist.

A frozen app is resumed after three weeks. Walk the E6 sequence and say where a stale waker dies.

Mint a fresh epoch; write the fenced takeover seal into the manifest by CAS — here a stale waker dies, because its seal loses the CAS against a manifest that has moved on; then reconcile the local /data disk against durable history (rebuild if diverged); only then does the guest run.

PT-9's slow waker never sends a single WAL append. Why is it still dangerous, and which rule stops it?

Its damage is a snapshot registration: a manifest stamped with the old epoch whose contents include the successor's newer data — forged lineage that later poisons restores and GC. The gateway append fence (E3) never gets a chance to fire. Registration fencing (E5) — rejecting a manifest stamped below the current epoch — is the only fence on that path.

Why does CI deliberately break the protocol three ways and demand failure?

A safety property that still "passes" with its enforcement disabled isn't being exercised by the model — the pass is vacuous. Requiring each disabled fence to produce a counterexample proves the model actually depends on every fence it claims to verify.

The doorman

What you'll learn
  • The difference between authentication (who are you?) and authorization (what may you do?) — and why apps here implement neither
  • The identity-aware proxy pattern: one front door for a million apps
  • Why "un-share" taking effect on the very next click falls out of the architecture for free

Unlike the previous chapters, this one describes a design, not shipped code — M4 is the next milestone. It earns its place in the book because it completes the founding analogy: a document isn't really a document until you can share it.

The concept

4.1 Two questions that must never be confused

Authentication answers "who is this?" — proving the visitor is friend@gmail.com. Authorization answers "what may they do?" — checking that address against a guest list. Most apps bundle both inside themselves: a login page, a password table, role checks scattered through the code. For agent-written small software that bundle is a disaster three times over: every app reinvents security-critical code (written by an AI, at that), every user faces a new signup per app, and revoking someone means hoping each app's homemade logic works.

Krill's answer is the same stance it took with data: take the dangerous job away from the app entirely. Apps contain zero auth code. Both questions are answered before a request ever reaches the microVM.

The concept

4.2 The identity-aware proxy

Chapter 1 put a reverse proxy in front of every app to hold requests for sleeping apps. That choke point now earns a second job. Every request first meets the platform's edge, which authenticates the person (via Google OAuth — Krill never sees a password; it delegates "who are you" to an identity provider the visitor already trusts), then consults the app's share list, and only then forwards the request inward — wearing a name tag. This pattern has a name in industry — an identity-aware proxy — and it is what Google's IAP and Cloudflare Access sell to enterprises. Krill builds a small one and makes it the default for every app.

4.3 Sharing on three planes

The share sheet from the explainer distinguishes three separately grantable powers, because "can open the app" has quietly become three different trusts:

PlaneGrantsWorth noticing
UseOpen the app, act through its UIThe default share; a domain share ("anyone at example.com") covers a whole team at once
EditChange the app itself — redeploy itIncreasingly means their AI assistant can change the app too; a real decision, not a checkbox
DataRead the app's database beneath the UIBeing allowed to use an app doesn't mean reading everything others typed into it

And the property that makes the whole design click: because every request passes the doorman, revocation is instant. Remove someone from the list and their very next click is refused — no passwords to rotate, nothing to redeploy, no app cooperation required. Compare that with the app-embedded world, where "remove access" means trusting each app's own session logic. It's the same architectural move as Chapter 3: put the check at a choke point the untrusted party can't route around. Epochs fence writes; the doorman fences people.

4.4 The gate, and the road past it

M4's acceptance gate is refreshingly non-numeric: a non-technical friend opens a shared link and uses an app with zero setup — no signup, no install, just the Google account they already have. (A quiet side effect: if recipients keep coming back, the market-demand experiment this project explicitly declined to run starts running itself for free.)

A build-vs-buy note, recorded as ROADMAP decision #8: only the parts of this chapter that are the product get hand-written — the three-plane ACL, share links, the per-app token scoping, the marriage to the wake hold. The commodity plumbing around them (the OAuth dance, session cookies, JWT/JWKS handling) is assembled from proven components in the oauth2-proxy mold, because auth plumbing is the highest security-bug-density code in software and none of it is differentiated. The same posture holds platform-wide: the verified core from Chapter 3 has no off-the-shelf equivalent and stays; the perimeter — build isolation, guest egress fencing (kernel netfilter, so an agent-written app can't reach the cloud metadata service or send spam under the platform's IP), multi-host lease minting (etcd), even the ext4 tailer (retired by host-served block devices, someday) — leans on software with decades of adversarial hardening.

The design also extends cleanly past the milestone. Swapping "Google" for "the customer's identity provider" — Okta, Entra ID, a SAML endpoint — turns the doorman into a federation broker without touching sessions, ACLs, or the signed header: exactly the shape enterprises already buy. That, along with a second host (making PT-1 a live-fire exercise), lazy restore, and custom domains, sits in M5's dessert tray.

If you remember one thing

M4 applies the book's one recurring idea to people instead of data: never ask the untrusted party to enforce anything. Identity is checked at a choke point every request must cross — so sharing is one click, and un-sharing is the very next one.

Check yourself
Why is the identity JWT scoped to a single app?

Without scoping, a token proving "this is friend@gmail.com" to one app could be captured and replayed against any other app — any app you can use could impersonate you everywhere. Binding the token's audience to one app makes it worthless anywhere else.

Why does revocation take effect on the next click, with nothing redeployed?

Because no app holds its own sessions or credentials. Access is evaluated fresh at the doorman on every request, so changing the list changes the answer immediately — the app never knew who was allowed in the first place.

Which earlier design decisions does the doorman rhyme with?

Chapter 0's stance (the guest is untrusted — so auth lives host-side, like WAL shipping), Chapter 1's router (the choke point already exists; auth is its second job), and Chapter 3's fencing (correctness enforced at a layer the stale or unauthorized party cannot bypass).

Epilogue

One idea, four times

Strip the milestones to their skeletons and the same theorem appears four times. M1: don't keep machines alive — make their absence undetectable. M2: don't trust a deploy — watch it serve. M3: don't prevent stale writers — make staleness powerless, and let a model checker, not a reviewer, say when you're done. M4: don't let apps guard their own doors — put one guard where every path already passes.

In each case the system declines to rely on the component least able to be trusted — a sleeping VM's sense of time, a build's optimism, a zombie's self-awareness, an AI-written app's security code — and moves the responsibility to a small, host-side mechanism that checks a simple fact: a probe, a postcondition, an integer comparison, a list. That is the whole trick, and it is enough to let a million tiny apps sleep soundly.
